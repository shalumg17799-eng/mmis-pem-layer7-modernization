## What the numbers do and do not say

- **The targets are placeholders.** Every target in nfr.md is DEFAULT until the user gives volumes and service levels, so MET means "met against the placeholder", not "agreed".
- **The machine was not quiet.** Docker Desktop was running about 26 containers of other projects next to the ten PEM services; free memory at the start was 1,169 MB of 16 GB, the runner waited 480 s in total for 1,024 MB
  (its own gate), 8 logical processors at 46 % load at the start, and other processes may have run during the measurements (the runner cannot see them). The k6 step took 614.8 s instead of about 2 minutes, almost all of it memory waits.
  The search maximum of 4,329 ms is a single slow request (the first requests after the load); p95 and p99 (212 ms) are not affected.
- **One JVM for ten services.** The PEM services run in one JVM with a 512 MB heap (ADR-011), so the figures are for that run mode, not for ten separately sized containers.
- **Gap, recorded, not tuned away:** this smoke runs 20 concurrent users. It does **not** exhaust the gateway's connection pool (200 connections, no wait limit for a connection: Apache's 3 minutes apply). The review of the
  gateway upgrade on 2026-11-24 suggested a wait limit of about 2 s and a per-service limit below the total (MAM-29 report, "Review fix 3"; `review-should-fix.md`; Q-157). A test of that case needs 200 concurrent slow calls to one service;
  it is not part of MAM-88 as written. Proposal: a story for the pool limits, test first.
